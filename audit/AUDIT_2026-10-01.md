## Security and reliability fixes

The generated pre-fix security scan identified five medium findings; see [baseline report](security-baseline-report.md). Its scope is source review, with live infrastructure and conditional RSS risks explicitly incomplete.

- Public Payload local queries now enforce collection and field access, including detail pages, metadata, lists, globals, sitemap and related content. Regression tests reject draft-only records.
- Internal research notes and open questions require an authenticated editor. Anonymous API responses and client props no longer contain those fields. Existing public source citations derived from internal notes consequently disappear; use a separate explicitly public source field if those citations are needed.
- JSON-LD serialization escapes literal `<` correctly throughout public pages, blocking script termination from stored values.
- Sponsor click tracking uses React handlers with values as data instead of generated executable strings and per-card global listeners.
- Manual cache revalidation accepts authenticated POST requests only, validates a public path, and returns 503 when REVALIDATE_SECRET is absent. Existing CMS change hooks remain the normal automatic invalidation path.
- Claim submissions now report provider delivery failures instead of false success.
- Matched Payload dependencies upgraded to 3.90.2; Next and eslint-config-next to 16.3.8; vulnerable transitive DOMPurify/Undici versions constrained. Final npm audit reports zero known vulnerabilities across installed dependencies.
- Fixed the no-featured-story homepage link to /stories. Unconfigured sponsorship/gallery rendering avoids attempting a localhost database connection.

## Before deployment

1. Review and apply [neighborhood enum upgrade](neighborhood-enum-upgrade.sql) against the intended PostgreSQL database, or generate/apply the equivalent Payload migration. It adds values to discovered main/version neighborhood enums without modifying records. It has NOT been executed or tested against the live schema; non-public schemas/custom table names require adaptation.
2. Configure REVALIDATE_SECRET if manual cache revalidation is used, and update any caller to authenticated POST with a JSON path. NOTION_SYNC_SECRET must be configured for local authenticated webhook testing too.
3. Inspect the Notion automation field selection. Include Neighborhood, Neighborhood Context, Description, Business Name, Category and Profile Slug; use the existing sync secret securely. Source data alone does not establish actual outgoing payload selection.
4. After deployment, re-sync an existing published profile using its stable Profile Slug and check the CMS record, visible profile and metadata. Without a consistent slug the existing slug-based upsert may create a duplicate. Do not bulk re-sync until one controlled record is verified.
5. Complete live verification of collection ACLs, authenticated editor behavior and existing published content on a preview/environment with an isolated database before promotion.

## Remaining limits / follow-ups

No confirmed critical/high application exploit remained in the reviewed source, but this is not a guarantee of production security. Live hosting configuration, secrets, database permissions and actual webhook execution were not tested. Conditional RSS fetch risks remain: remote image URL/redirect constraints and download limits need explicit hardening if feed content is untrusted; the review did not establish attacker control of that source. Review event replacement/media deletion behavior before job changes. In-memory rate limiting is per-instance and is not a distributed production abuse control. Production Payload configuration retains the existing push setting; a controlled migration strategy is preferable to relying on schema push. The audit did not change unrelated editorial data or claim all Notion properties are intended for the directory schema.
